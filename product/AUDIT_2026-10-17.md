# Product and Technical Audit

Audit date: 2026-10-17, approximately 16:45-17:00 America/Chicago.
Application baseline: `3998465` on `main`; predecessor `154e990`.
Scope: code, git history, GitHub metadata, safe production requests, local tests,
isolated mock reproductions, and desktop/mobile browser inspection.

## Executive assessment

Daily Technicals is a functioning research prototype. The live ranked scan,
daily candlesticks, SMA/AVWAP overlays and review actions work in the tested paths.
It has not yet established ranking usefulness, complete earnings history, or
reliable latest-session coverage under failure conditions.

The morning engine is not ready to be trusted with live execution. Access control,
order lifecycle, persistence and risk-accounting defects are higher priority than
adding signals. Production reported AUTO ON and broker connected, but account
mode was not disclosed by the status response. No live trading authority was
changed and no broker order was submitted by the audit.

## Findings, ordered by severity

Severity: P0 = execution/security release blocker; P1 = core correctness or
availability; P2 = important usability/operability gap. Severity is separate from
the roadmap: execution repairs can be deferred only behind a verified isolation
gate, not left reachable while research features ship.

### F01 / P0: Trading controls lack application authentication

Evidence: [server](../app/api/server.py), lines 31, 45, 79, 96 and 117. No global
authentication middleware or route dependencies protect approvals, closes, risk
settings or automation changes. Production GETs to status and OpenAPI succeeded
without credentials; OpenAPI declared no security scheme. Broker/account data is
also exposed through unprotected reads. No mutating production trading route was
called, so exploitation was not exercised.

Impact: anyone able to reach the service may operate its trading authority or
inspect account information. Public deployment is verified; deployment-side
protection for mutating requests was not independently configured or observed.
Action: KT-001. Require server-enforced identity/authorization and execution mode
boundaries before considering live use; protecting or hiding buttons is not enough.

### F02 / P0: Supabase writes do not restore state or daily risk after restart

Evidence: [store](../app/db/store.py), lines 96-104 and 136; [risk](../app/engine/risk.py),
lines 41-45; [orchestrator](../app/engine/orchestrator.py), line 74. SupabaseStore
starts from empty dictionaries, mirrors writes, and performs no startup reads.
Trade rows omit broker order IDs and pending-exit state. Startup does not reconcile
broker positions/orders, and RiskManager starts its counters at zero.

Mock reproduction: one saved open trade became zero tracked trades in a second
SupabaseStore, with no select call. A risk manager blocked after a synthetic
$125 loss became allowed in a new instance with zero trades and zero loss.
These were isolated local objects, not production or broker losses.

Impact: deploy/restart can orphan pending-exit supervision, lose dashboard truth,
and reset daily limits even with Supabase configured. Action: KT-003.

### F03 / P0: Order submission is confused with confirmed position state

Evidence: [trader](../app/engine/trader.py), lines 53-68, 80-90 and 94-114;
[Alpaca synchronization](../app/data/alpaca.py), line 483;
[close API handler](../app/engine/orchestrator.py), line 528.

Regular entry submission creates an OPEN trade before fill confirmation. Manual
close records CLOSED and realized P&L using a quote immediately after submission,
without waiting for the close fill. Repeated close calls have no closed-state or
idempotency guard. Regular bracket exits are not reconciled by refresh_marks;
Alpaca sync only considers pending extended entries.

Mock reproduction: an explicitly unfilled close-order response still produced
CLOSED and synthetic $10 realized P&L; closing the same Trade twice submitted two
broker-close calls. This does not prove a real unwanted fill occurred, but exposes
the path. Action: KT-002. Treat all existing app P&L as unverified, not analytics
evidence for strategy quality.

### F04 / P0: Pending extended entries bypass the daily trade-count reservation

Evidence: [trader](../app/engine/trader.py), lines 67-68 and 102-104;
[Alpaca](../app/data/alpaca.py), lines 479-502;
[mark interval](../app/engine/orchestrator.py), line 35.

Mock reproduction: with max trades/day = 2, three accepted pending-exit entries
were submitted and the risk trade count remained zero. Multiple pending entries
can therefore later fill beyond the intended cap. Partial fills are not protected
by the current FILLED-only exit-attachment condition; cancellation after a partial
fill can be treated as terminal without tracking the remaining position.

Exit attachment is polled approximately once per minute and depends on the app
remaining alive. It must not be represented as guaranteed premarket stop
protection. Alpaca documents that only eligible limit orders execute in extended
hours and that brackets do not support extended hours. [Provider order rules](https://docs.alpaca.markets/us/docs/orders-at-alpaca).
Action: KT-004; default planning recommendation is no new extended-hours execution
until supported protection and failure behavior are explicitly validated.

### F05 / P1: The live morning scanner is paused by a provider dependency

Observed production status: broker connected, IEX, AUTO ON, zero active detectors,
and "Russell 1000 membership unavailable; scan paused while this filter is enabled."
The market was closed during the audit; this is not an intraday latency test.

Evidence: [filter](../app/data/scan_data.py), lines 61-75;
[membership proxy](../app/data/finnhub.py), line 69. The default filter depends on
IWB ETF holdings from Finnhub. Fail-closed behavior is appropriate. The response
does not identify whether entitlement, an empty response, provider coverage, or
an outage caused the failure. Do not silently widen the universe. Action: KT-005.

### F06 / P1: Earnings request success does not establish historical coverage

Live GET for AAPL, five years: status available, one event, 2026-11-02 scheduled
after close, and zero historical events. The ABBV five-year browser chart also
reported one date. Dates were not independently validated against issuer sources.

Evidence: [calendar status](../app/data/daily_research.py), line 171, labels any
error-free sequence available, including empty historical responses. The UI
discloses provider limitations but still cannot distinguish scheduled-only data
from a complete history. Earnings-reaction AVWAP may be unavailable as a result.
Action: KT-007; contract/coverage validation before promising earnings on history.

### F07 / P1: Latest-session freshness is not an exchange-calendar contract

Evidence: [normalization](../app/data/daily_research.py), line 42, always excludes
today, including after close; [ranking](../app/engine/technicals.py), lines 73 and
145, accepts up to five calendar days of age. [Market hours](../app/data/market_hours.py)
uses weekdays and fixed hours, not holidays or early closes.

Reproduction: a synthetic chart last dated Monday 2026-10-12 remained eligible on
Friday 2026-10-16 without a stale warning. Live audit data was current through
2026-10-16; no stale live candidate was observed. Risk: several missing sessions
can still enter a "daily" queue, and same-evening review omits the just-closed day.
Action: KT-006. Agree on premarket versus after-close publication semantics.

### F08 / P1: Rankings are not validated opportunity quality or execution liquidity

Evidence: [daily-v2](../app/engine/technicals.py), lines 107-145;
[universe](../app/data/daily_research.py), line 19. Scores are documented heuristics;
there is no point-in-time outcome dataset or out-of-sample evaluation. Thin daily
turnover subtracts points rather than excluding a candidate. The default list is
62 stocks, so "best" means within that declared list, not the whole market.

IEX is one venue, whereas SIP consolidates exchange activity; the two can produce
different volume, VWAP and liquidity observations. [Alpaca data FAQ](https://docs.alpaca.markets/us/docs/market-data-faq).
No paid upgrade is necessarily required for delayed daily research: test historical
SIP entitlement separately from real-time execution entitlement before spending.
Actions: KT-008 and KT-012. Do not infer borrow availability or short suitability
from a bearish chart score.

### F09 / P2: Shared locks can couple chart latency to unrelated calendar work

Evidence: [research client](../app/data/daily_research.py), lines 99, 136, 181 and
200. Bars are globally serialized; calendars are globally serialized and split
into sequential windows. Scan and chart summaries await the upcoming calendar.
Each HTTP request has a 25-second timeout; there is no bounded whole-operation
deadline. Aborted browser earnings requests are not a proven server cancellation
contract.

Controlled mock: with each provider request taking 60ms, a five-window upcoming
calendar took 655ms behind a concurrent five-year calendar instead of roughly
300ms in isolation. This reproduces head-of-line delay, not production p95.
Action: KT-009. Preserve the good warm-path performance; measure cold and degraded
providers before introducing infrastructure.

### F10 / P2: Long-range annotation density undermines quick chart inspection

Observed on live ABBV and PFE five-year daily charts: many historical cross labels
overlap candles and each other. [Marker construction](../app/web/technicals.js),
line 191, labels every selected historical event; crosses default on in
[HTML](../app/web/technicals.html), line 54. Rendering is technically nonblank but
the resulting visual density obscures the chart, especially at 390px. Action:
KT-010; preserve daily candles and offer sparse annotations at long ranges.

### F11 / P2: Morning dashboard is clipped on mobile

Live 390px test: document width 390px, internal workspace width 1366px, with body
overflow hidden. Right-side controls and opportunity context are offscreen.
Evidence: [morning layout](../app/web/index.html), lines 15 and 44. Daily Technicals
did not horizontally overflow in the same mobile check. Action: KT-013; priority
depends on whether morning mobile trading remains in scope.

### F12 / P2: No durable product evidence loop or automated release test gate

Repository search found no product analytics SDK/event pipeline, and no tracked
`.github` workflow. Review decisions and picks are browser localStorage, not
durable multi-device analytics. Python/JS tests are useful but do not cover full
broker fill lifecycle, auth, or recovery. Requirements mostly use open lower
bounds and browser tests depend on an external local Playwright runtime.

The README's historical overview still describes FMP/IBKR, a $5 filter and AI
weighting that the current section supersedes. This is confusing operational
documentation, even though the precedence warning is explicit. Actions: KT-011,
KT-014 and KT-015. Railway deployment success is not proof of test coverage.

## Architecture and ownership boundaries

| Layer | Current implementation | Product consequence |
| --- | --- | --- |
| Web | Vanilla JS; separate morning and daily pages; Lightweight Charts via CDN | Simple stack; external script availability is a runtime dependency |
| API | FastAPI routes and static files in one process | Research routes are read-only, but process startup still runs the trading orchestrator |
| Morning data | Finnhub earnings/caps/IWB holdings; Alpaca movers, snapshots, minute bars; optional IBKR | Coverage and entitlements govern whether setups exist at all |
| Morning engine | Scan, completed-bar detector, technical scoring, execution validation, trader/risk | Configured polling is not observed feed-to-screen latency |
| Daily data | Dedicated async Alpaca history/Finnhub client, bounded in-memory caches | Independent of order methods, not independent of app availability |
| Daily model | ta/pandas SMA/ATR plus range/cross/AVWAP logic | Transparent score; no empirical calibration |
| State | Optional Supabase write mirror, process dictionaries, browser localStorage | No reliable restart or cross-device continuity |
| Deployment | Railway starts uvicorn directly | No visible test gate or separately supervised execution worker |

## Reproduce the safe baseline

From the repository on this machine:

```powershell
.venv\Scripts\python.exe -m pytest -q
node --test tests/test_dashboard.cjs tests/test_technicals.cjs
$env:NODE_PATH = 'C:\Users\david\.cache\codex-runtimes\codex-primary-runtime\dependencies\node\node_modules'
$env:BROWSER_CHANNEL = 'msedge'
node tests/browser_technicals.cjs
```

Browser fixture tests expect the offline preview on port 8012. That preview was
already running with `--lifespan off`, preventing background broker startup.
For fresh testing, use blank credentials and automation disabled as well. Do not
start a second production-configured orchestrator just to test the UI.

The defect probes used mocked broker methods, mocked Supabase create_client, and
synthetic daily bars in a separate process. Future fixes should convert their
scenarios into permanent regression tests with the desired correct assertions.
No load test, exchange-open soak, real order, live risk change, database migration,
or score-performance backtest was performed.
